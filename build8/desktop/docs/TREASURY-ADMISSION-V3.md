# Treasury verifier issuance and identified admission store V3

Status: approved implementation; focused Windows unit/integration/tool and isolated historical conformance checks pass. Final mixed-source/native qualification remains pending. Supersedes unrestricted V2 runtime admission semantics. Public TEST-VALUE software work only. Production create/open/issue/admit stays fail-closed; deployment requires protected rollback-resistant state rooted outside restored storage or a separately authorized fail-closed recovery rule. No such production state/input is supplied here.

Authority: Build8-Codex-Takeover-Order-20261004.txt, ceremony nonce/store rollback lines 273-284, and prior Architect continuation ceremony requirements. Existing 14-item challenge, TreasuryProofOfControl domain/intent, descriptor, phase/class, context construction and signature bytes stay unchanged. V3 names the verifier/store API and schema, not a new signed challenge version. No TTL, production context bytes, authority or trust roots are invented.

Creation returns a random StoreIdentity, not an admission-capable handle. An operator must pin the expected ID independently. open/open_read_only require that trusted ID. Missing/zero ID is refused, and exact schema/context/record/ID validation happens before writable connection configuration. No autocreation or migration occurs on open. A read-only preflight validates the identified file first, and a second validation occurs on the operational connection. A hot journal that requires write recovery in the file observed by read-only preflight is refused. Writable open then uses a newly opened SQLite connection: a path substitution between the two connections can cause SQLite to recover a substituted hot journal before its binding is rejected. Repeated logical identity checks do not provide an OS-handle/path-substitution barrier, and rejection does not promise that such substituted bytes remained unchanged. Use controlled private storage and ancestors for this local TEST-VALUE model; those permissions reduce lower-privilege substitution but do not defend against a same-account or administrator adversary. Safe writable handle binding would require separate reviewed platform/VFS work. No recovery of historical evidence is authorized through this API. Fresh and copied databases are not accepted by discovering their identity and calling it trusted.

issue(expect, exact_descriptor, denylist) is the only current challenge creation route. It validates the descriptor against the trusted Expect generation/descriptor hash and Treasury identity and checks its decoded public key against the configured denylist before the RNG, draws a fresh nonzero 32-byte nonce internally with the OS cryptographic RNG, builds the existing challenge, and commits its exact challenge and descriptor bytes into the identified store. The challenge already binds phase, class, network, context, authority, Treasury-record hash and generation. No prover nonce parameter is exposed. A returned challenge therefore exists in the durable issuance registry before signing can be requested.

Both issue and admit recheck exact schema, context, record hash and the trusted store ID inside their IMMEDIATE write transaction before issuing or consuming. This rejects a binding substitution committed during cryptographic validation. admit performs the existing strict/cryptographic/expectation checks, then uses one IMMEDIATE transaction to require the exact registered challenge and descriptor, reject an unknown issuance or mismatched bytes, reject consumed issuance as Replay, mark it consumed and insert the exact signature/admission bytes. Both writes commit atomically or neither survives. The trusted store binding is checked before acceptance or consumption. Failed proof validation leaves issuance unconsumed. The currently supplied denylist applies consistently to issuance, admission and authenticated audit; a descriptor issued under an earlier list does not bypass a later denial. Concurrent attempts serialize and admit once. A signing-session retry is allowed to reuse an unconsumed issued challenge; a new signature over already admitted challenge is not a second admission.

Read-only recorded/admissions perform structural exact-byte and consumed-issuance association checks only. Cryptographic authenticated verification occurs through verify_issued/audit_recorded; manifest/verify_frozen invoke that authenticated audit. They never issue or consume, and repeated identical admitted-proof checks remain repeatable. Frozen Genesis checks retain their independent approval pin and complete descriptor/Parameters comparison; the store ID must also equal the approved manifest ID.

TEST-VALUE SQLite state has an explicit limit: a same-ID snapshot copied together with the database can restore consumed issuance. Store IDs, hashes and copied authentication keys cannot prove anti-rollback. Tests must demonstrate this limitation and the unconditional Production refusal, rather than label a database-only replay check as production rollback resistance. Existing Windows EXTRA directory-sync limitations remain stated.

Historical V1/V2 vectors, schema prose and reproduction inputs remain byte-identical. Their old-source admission sequence conformance runs only in a clearly isolated legacy test model. Current executable public tooling and runtime imports use V3. A new current-source mapping records exact successor source/test hashes and statuses; historical PASS is never silently assigned to V3.

Required successor checks: OS-issued registry before signing; unknown prover nonce refusal; exact trusted ID before writable configure and before admit/issue; foreign context/phase/authority/generation/descriptor refusals; same-nonce and concurrent replay; failure between consume and admission commit; restart; identical read-only audit/file hashes; foreign-schema refusal without migration; immutable historical artifacts; explicit same-ID snapshot limitation; fail-closed Production create/open/issue/admit. All cryptographic positives require both signature components. Evidence preserves failures/partial runs and distinguishes software checks from physical custody.

Operator sequence for the current public example (all public TEST-VALUE inputs): create-store with the trusted Treasury descriptor/record pin/context; independently record and approve the returned store_id; challenge with --generation, the trusted succession inputs when generation 2, --store and --expected-store-id; sign that exact public challenge using the separate TEST-VALUE key tool; verify and admit with the same trusted ID; manifest and verify-frozen with the same ID and independently pinned approved manifest. Old --nonce-label/--os-nonce challenge flags are refused: nonce selection belongs to the identified verifier. An existing challenge output is preserved and refused by challenge; reuse its bytes for a signing-session retry. Issuance committed before a subsequent output-file error is retained, never silently deleted. Secret handling, production signing, sealing and publication remain outside this implementation.
