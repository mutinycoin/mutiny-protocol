# Treasury antirollback mechanism and remaining adoption decision

Status: trust model adopted by direct human reply on 2026-10-05 for implementation and TEST-VALUE verification. This does not enable Production, create custody material, provision a TPM or authorize a production ceremony. V3 issuance and atomic database consumption remain unchanged until a reviewed successor is integrated.

The human approval accepts the operational trust dependency, restricted to Treasury verifier issuance/consumption. It grants no spending, destination, monetary, membership or quorum authority and must not become a live dependency of ordinary consensus, general enrollment, routine payment or historical replay. Protect enrollment/rotation and latest-state monotonicity outside the database restore domain. Bind operations and exact contents, serialize conflicts, acknowledge only durable external transitions, require completed SQLite commit before local success, and treat timeout as UNKNOWN. Conflicting retries fail; identical retries identify the same operation/outcome without another logical admission. Ambiguity freezes both paths until authenticated exact reconciliation; unreconstructable state remains frozen. No new proof format, committee, quorum, TTL or consensus semantics are authorized. Real authenticated trust boundary, reconciliation and native storage remain production prerequisites; simulated failures and power-loss evidence are separate classes.

## Exact gap

The takeover requires state protected against rollback outside the restored admission database, or an explicitly approved fail-closed recovery rule rooted outside that database. Current `AdmissionStore` has neither. An expected random store ID, checksum, copied MAC key and a second SQLite binding check do not detect restoration of an earlier same-ID issuance. Production is consequently refused. Separately, the read-only preflight/new writable-open path can recover a substituted hot journal before rejecting its identity. This is an unfinished platform/VFS problem, not physical qualification alone.

## Proposed mechanism

Adopt an external verifier continuity service with a separately protected monotonic record for each independently pinned `(network, ceremony context, Treasury record, verifier identity, store identity)`. It stores an ordered set of reserved issuance commitments and terminal consumption commitments. The service is outside the database's backup/restore and access domain. Its authoritative record cannot be discovered from the presented database. No consensus operation, voting committee, fee, nonce TTL or proof encoding is added.

For issuance, first authenticate the service's CURRENT ordered state and expected high-water mark; membership of a reservation in an old signed history is insufficient. The verifier draws the existing-format nonce using the OS CSPRNG, reserves the exact challenge and descriptor commitment with the continuity service, then writes the exact issuance to the V3-style database transaction. Only a matching durable database issuance AND matching current external reservation can be returned for signing. Reservation without a completed database write remains withheld; ordinary reopen cannot turn it into a returned challenge. Store identity and full context must be authenticated before either reservation or mutation. Enrollment and rotation of the service/store identity pins are separately protected; a restored database cannot nominate a fresh continuity identity to bypass its old terminal history.

For admission, fully verify both signature components, expected authority/context/generation and exact issued bytes first. Obtain a linearizable external terminal consumption of that exact issuance and signature commitment, then atomically consume the database issuance and insert the admission as today. The response explicitly distinguishes NEW terminal transition from ALREADY terminal: only NEW permits this ordinary admission attempt; ALREADY is Replay, even if a restored database presents an unconsumed row. Identical service requests may retrieve the original result for diagnosis but cannot authorize a second admission. External consumption is irrevocable. If the external step succeeds but SQLite fails or the process crashes, further admission AND issuance are refused and the store enters reconciliation-required state. Pending/in-doubt status resides in the protected service, not only the restorable database. It must not undo consumption, accept an older snapshot, or report a successful admission that lacks the durable exact database row. A recovery tool may restore the exact already-authorized row only from authenticated retained bytes matching the terminal external commitment, under a separately reviewed recovery contract; no new admission or signature is authorized by reconciliation.

Read-only verification of the exact admitted proof stays repeatable. A second admission of a terminal issuance is Replay. Wrong context, unavailable service, rollback, ambiguous external outcome, lost authenticated bytes or divergent terminal commitments fail closed before acceptance. Existing records and failures remain available for audit; the service outage sacrifices admission availability rather than weakening freshness.

The external store must retain the exact bounded public challenge, descriptor and signature bytes (not only a locator) plus authenticated ordering records sufficient for replay/reconciliation. A hash alone cannot recover evidence. State/evidence bounds and backpressure must be explicit before implementation closure; the current proposal uses the existing fixed proof/descriptor limits and one ordered pending transition per verifier. No old evidence is evicted to regain capacity.

## Trust assumptions and decision

Approve, or reject, reliance on a separately administered protected verifier continuity service whose monotonicity, authentication and latest-state availability are trusted. Its administrator must not be the principal able to restore the admission database; deployment evidence must establish this separation. An ordinary second SQLite database, file, same-account daemon, user-writable counter, unsigned remote response or token copied with a backup is NOT this service. Cryptographic authentication of an old response alone is insufficient: a fresh authenticated service session and linearizable current-state check are required. This model introduces an explicit non-consensus operational trust dependency; it does not invent a quorum or committee.

If this trust model is unacceptable, keep production refusal and select an alternative concrete rooted recovery policy. Do not call an unimplemented monotonic provider a missing TPM certificate or a completed physical-input dependency. The proposed protocol can be tested against a clearly labelled isolated in-memory service model; that demonstrates software safety and outage behavior only.

## Platform work and acceptance

Before enabling any production writable path, implement a reviewed SQLite VFS/platform binding that retains verified OS file identity through preflight and operational open, refuses reparse/symlink and unsafe ancestor substitution, and pins every recovery sidecar consistently. Checking paths twice is insufficient. Windows sharing-mode handle pinning and POSIX descriptor/VFS opening require separate actual native controls; no permissions change to existing evidence is authorized.

Acceptance must demonstrate: restoration of an earlier same-ID database after consumption; copied database/key/service token refusal; concurrent consumption admitting at most once; new and repeated nonce attempts; valid and invalid hybrid proofs; context/store/authority substitution before any protected-state change; crash at every external/SQLite boundary; unavailable and delayed/stale/forged service responses; restart with missing or divergent protected state; exact terminal-row recovery without second admission; repeatable unchanged read-only audit; bounded evidence availability; hot-journal/path substitution refusal before mutation; and retained unconditional Production refusal until a real protected backend and independently approved production context are present.

This packet does not change V1/V2 historical vectors, the 14-item challenge or existing monetary rights. Final source, provider protocol, bounds, native platform implementation and actual deployment identities remain review and campaign requirements.
