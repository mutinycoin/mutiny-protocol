# Path B admission amendment, 2026-10-05

Status: direct DESIGN authorization; implementation and physical qualification remain in progress. Source decision is retained byte-for-byte in CODEX-PATH-B-USER-DECISION-20261005.txt. It supersedes prior K2/A6 hard stop E only where the stop depended on physical-host node execution or exclusion of forwarding. Historical failed/partial evidence and the prior decisions remain preserved.

The admission invariant is one qualifying physical TPM, one canonical voting/reputation lineage across active membership and pending admission. Remote/VM execution and forwarding are accepted, with no locality claim. Software TPM/vTPM alone cannot qualify. Public identifying EK evidence distribution stays within the earlier narrow permission; no activation/private secrets enter public witnesses.

Implementation boundaries:

1. Independently approved physical hardware classes must specify their authenticated stable identity and complete supported alias relationships, including RSA/ECC templates, certificate reissuance and AK changes. Canonical key/DER normalization addresses alternate representations of one key; it does not link two different EK keys to one TPM. A per-EK digest cannot substitute for missing platform evidence. Classes lacking demonstrated physical uniqueness stay unqualified.
2. Native admission verifies those relationships and fresh actual credential activation before issuing an authenticated identity capability. Active and pending registries use the same canonical lineage and reject a second independent admission atomically. Rotation/recovery may update that existing lineage only through their existing authorizations and possession proofs, never via duplicate presentation.
3. MakeCredential must use validated EK credentials and exact AK attributes/Name, a fresh challenge, and approved network/Genesis/rule context. ActivateCredential response is checked by the specified verifier mechanism; a claimant-created success transcript or signed result is insufficient. Changed AKs need fresh linkage. Exact hybrid BOTH_REQUIRED consensus tuple remains typed and authorized; AKs and consensus keys are distinct.
4. A2 root/intermediate/EK revocation, pending cancellation, immediate resulting-state exclusion and protected monetary/history semantics apply unchanged. Revoked physical lineages cannot be resurrected through an alias. Failed transitions must leave canonical bytes unchanged and preserve old obligations.
5. Host/client process count, TPM speed and network latency never determine uniqueness. Do not add relay penalties, artificial timing tests, DRTM, TEE or PUF. PCRs describe the TPM platform; no remote VM measurement or key-residency claim follows from a quote hash.

Activation protocol completion requirements remain precise. Existing witness commitments to credential/seed/secret hashes and a signed activation-result record cannot establish an independently replayable activation by themselves. The prior multi-challenger sketch remains unadopted: Path B does not choose a new threshold, challenge window, challenge/response/reveal carrier, fee rule or withholding disposition. Implementation must use a concrete stated verifier trust model and authenticated available evidence, without inventing those policy inputs. Test-only command/codec adapters and negative tests may continue; unsupported production transitions fail for missing activation/hardware/uniqueness requirements, rather than for node locality.

Acceptance matrix: concurrent clients and pending/active races share one lineage; supported EK aliases and reissued certificates cannot duplicate it; changed AK needs fresh activation; unrelated software keys, stale/substituted challenges and context/replay reuse reject; authorized rotation/recovery retains bond, age, reputation and penalty history; failed transactions and crash/reopen preserve uniqueness atomically; a valid forwarded exchange is accepted and produces at most one lineage; A2 revocation and monetary protections remain intact. Label simulation and TEST-VALUE separately from actual hardware evidence.

Remaining launch inputs: independently qualified physical class identities/alias evidence and roots/profiles; a concrete activation verifier mechanism and exact public evidence/context/availability rules; genuine physical MakeCredential/ActivateCredential and platform qualification records tied to candidate bytes. Proof of node execution on the TPM's physical host is removed as a dependency. Other clock, Genesis-binding and production restrictions remain unchanged. No TPM clearing, seed replacement, production signing, Genesis sealing or flashing is authorized.

Primary technical references, checked 2026-10-05: [tpm2_makecredential](https://tpm2-tools.readthedocs.io/en/stable/man/tpm2_makecredential.1/), [tpm2_activatecredential](https://tpm2-tools.readthedocs.io/en/stable/man/tpm2_activatecredential.1/), [TCG EK credential profile](https://trustedcomputinggroup.org/resource/http-trustedcomputinggroup-org-wp-content-uploads-tcg-ek-credential-profile/). Tool invocation availability is not physical qualification and is not production protocol selection.
