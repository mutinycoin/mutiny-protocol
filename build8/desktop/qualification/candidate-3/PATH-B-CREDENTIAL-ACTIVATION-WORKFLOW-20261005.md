# Path B credential activation and physical-lineage boundary

Source-only implementation proposal, 2026-10-05. Base: `ebbd15aaf988fa75c808dd2d031f45c2d2126ded`. No compiler, TPM operation, physical qualification, production admission, or publication is represented by this document.

## Authority and ownership

The user's 2026-10-05 Path B instruction supersedes execution-host association as a requirement. Qualifying physical TPM backing may be forwarded to a remote or VM node. It does not supersede physical authenticity, fresh key relationship verification, one physical TPM voting/reputation lineage, existing authorization, or the end of the unilateral Genesis ceremony authority at sealing.

IDX owns new `node/src/credential_activation_workflow.rs`, its explicitly included software tests, and this note in isolated worktree `build8-codex-path-b-activation`. It does not edit Hygiene's A2 admission/registry/retirement/recovery files, Root's ingress capacity files, Wallet's W15 files, shared module registrations, or any existing dependency lock. Those owners received the proposed boundary before source edits.

## Existing gaps, verified in the actual source

`activation.rs` is unrelated BFT activation kind 13. `attestation_witness::verify_witness` authenticates EK certificate chains, exact class templates, canonical public-key identities, witness commitments, and AK Name correspondence. Its `ActivationRecord` checks nonzero digests, not a fresh recovered activation secret. The signed provenance evidence digest is not that verification either.

`admission_v2::Admission::verify` and `node_admission_v2::Binding::verify` already check the exact hybrid descriptors, required owner authorization, Continuity possession, Node possession, generations, native certification and quote. BOTH_REQUIRED verification is delegated to the existing crypto API, not reconstructed as a quote hash or one key half.

`endorsement_identity::check_state` and the A2 successor enforce every committed identity across active/pending and retired records. These checks prevent reuse of known EK key identities; they do not prove that different RSA/ECC keys belong to the same chip or that an applicant disclosed all aliases. Canonical key normalization solves encoding/certificate reissue for the same key only.

## Local credential workflow

The new module is deliberately local verification machinery, not a consensus authorization capability. Its result cannot insert a member, allocate lineage/reputation, reset history, move a bond, or override the sealing rule. It is not registered into the shipping node launcher. A separate test target includes the source directly for later bounded validation.

1. Construct a candidate through existing complete typed binding verification, native strict AK public-area parsing and Name computation, and complete public witness verification against the same committed classes, trust roots and reference time. Retain the exact canonical binding checksum, profile commitment, computed AK Name, and ordered EK public areas/identities. The exact verified binding/profile commits the AK public bytes; MakeCredential needs the EK public area and AK Name, not a new abbreviated consensus tuple.
2. Obtain the current local canonical context from an owner-supplied provider, before and after constructing all challenges. The provider contract requires own-chain authenticated context, qualification and revocation checks; peer-provided fields and local success markers are not a provider. Scope binds network, Genesis, rule fingerprint, parent, transition purpose, exact authorized transition commitment, node, generations, full enrollment bytes, profile, classes and verifier trust policy.
3. Generate separate unpredictable 32-byte secret and 32-byte session nonce using existing `getrandom` for each attempt. A vetted MakeCredential adapter must use the exact certified EK public area and strict AK Name. The module does no RSA/ECC/KDF/encryption implementation. Private secret buffers use existing `zeroize::Zeroizing` and have no Debug/Clone/serialization. The adapter is a trusted local cryptographic dependency, not a claimant callback.
4. Only encrypted credential/seed bytes and the public scope/session identifier are delivered privately to the applicant. The expected raw secret is not delivered. Returned raw secret bytes must arrive through the authenticated enrollment channel and are hashed locally against the retained one-way commitment. Neither a claimed PASS, a submitted hash nor an old witness record is accepted instead. The first submitted response consumes the whole attempt, including malformed, wrong-context, wrong-class, replay or failed-secret responses; a second try needs fresh challenges.
5. Check current canonical context again at completion. Every ordered identity class must recover its own independently generated secret under the same exact AK Name; partial success produces no completed observation. A changed parent, authorization, revocation, class profile, transition or verifier policy refuses and consumes the attempt. Crash/restart intentionally loses pending attempts: no secret replay cache is persisted, and old replies cannot resume.

The returned observation records only public scope, session, ordered EK identities and hashes of encrypted objects. It omits secrets and secret commitments. It remains a local observation requiring an approved admission verifier trust model and qualified alias relationship before any canonical use. A malicious verifier knows the generated secrets and can fabricate its own observation; signatures on observations cannot remove that trust boundary.

Resource limits are caller-selected local limits, not new admission windows, thresholds, fees or consensus capacities. Secret equality uses the already approved SHA-256 commitment and a one-attempt policy; there is no claim of constant-time slice comparison. Adapter/transport errors are typed and omit child stdout, arbitrary error strings, paths or private payloads.

### Local elapsed freshness successor

The predecessor `e65737856fb7665862ce98e73ac48c5d818e2805` is preserved. Its unchanged-parent challenge could remain pending indefinitely; the source-only successor requires `Workflow::new(capacity, positive_local_lifetime)` or an explicitly trusted local `ElapsedClock` passed to `with_elapsed_source`. There is no implicit lifetime or disabled-expiry option. The caller chooses this finite local resource/freshness policy; it is not a new consensus admission window, active-key expiry, verifier quorum or physical C8 clock qualification. The default source uses process-local `Instant::checked_duration_since`; injected peer time and wall-clock timestamps do not satisfy the trusted-source contract.

The checked deadline starts before challenge generation and must still be in the future after adapter/current-context checks, before inspecting completion responses, and after the completion current-context check. Equality with the deadline is expired. A completion attempt removes the pending record first, including expiry/refusal. New issue requests consume all expired records before checking capacity, so they cannot block the local map forever. Deadline arithmetic overflow refuses before any credential adapter call. Unavailable elapsed time or a backward reading poisons this workflow and clears all pending commitments; later source recovery cannot reactivate them. A new workflow needs fresh unpredictable challenges. This is local freshness and replay handling, not durable tombstones, hostile-host antirollback, or evidence that canonical verifier authorization/physical relation inputs are available.

Six additional deterministic software-only controls cover just-before/at/after deadline, pre/post completion and post-issue elapsed checks, expired-capacity reuse without old response reuse, unavailable/backward time with all pending invalidated, post-provider time loss, and zero/overflow limits before adapter use. They use controlled elapsed values without sleeps and preserve the original fourteen modeled controls. Twenty prepared test functions remain uncompiled and unrun; no native or physical result is claimed.

## Actual production adapter requirements

A production adapter is not implemented by pretending to run a command. It must be pinned to a vetted implementation and tested against actual qualified TPM profiles. `tpm2_makecredential -T none` is an available documented no-TPM credential-generation mechanism, but the tools were not installed in the current Windows command inventory. No command was executed. The existing privileged TPM helper is a different signing/counter interface and is not silently extended with an invented command ABI.

The concrete adapter contract is `make_credential(exact_ek_public_area, exact_ak_name, private_secret) -> encrypted_credential_and_seed`. Its implementation must preserve exact nondefault templates, use private in-memory or protected-channel secret delivery, pin executable/dependency identities, bound output, refuse cpHash-only or simulated success, keep authorization material outside this interface, and exclude secrets from logs and public evidence. Activation is performed on the applicant's physical TPM through its supported, independently configured endpoint, which may be remote or forwarded. The verifier itself compares the recovered secret; an applicant-side result string is insufficient.

## Qualified class-specific physical equivalence

A promising mechanism is fresh activation of one exact nonduplicable AK under all mandatory certified EK classes, with strict fixedTPM/fixedParent/sensitiveDataOrigin/restricted signing attributes and fresh signed TPM attestation. This is a *qualification candidate*, not a generic mathematical assertion that any two keys map to one chip. Class qualification must establish the exact physical implementation's behavior, mandatory aliases/templates/nonces, certificate reissue and EK lifecycle, public-only/import/duplicate refusal, and seed/firmware changes. The TCG EK profile permits several EKs per TPM; it does not supply a universal chip identity simply by normalizing their encodings.

Before a physical equivalence result is accepted, supply an authenticated class qualification manifest defining the complete mandatory identity class list, trust roots, exact templates/nonces, allowed firmware, stable physical relation evidence format and verifier, plus qualification tests demonstrating that two separate TPMs cannot satisfy that class-specific relation. Applicant-selected subsets, unsigned serial numbers, arbitrary opaque labels, nonzero digests and witness-signature-only claims are refused. A class lacking a sound complete uniqueness method remains unqualified.

No `QualifiedPhysicalLineage` constructor is added from raw hashes or this local observation. That would disguise the missing authenticated relationship as a type wrapper. Once the relationship verifier is approved, its private constructor can carry the complete ordered identities and canonical lineage binding. AK change repeats fresh activation/linkage without releasing any EK aliases. Changed EK/template/seed/TPM is handled by the specified recovery path, never automatically admitted as fresh hardware.

## Canonical integration contract for the A2 owner

Hygiene's confirmed interfaces: `membership_v2::Book::get(node)` returns `Control`, whose binding retains exact `node_admission_v2::Binding`; pending status is an admission boundary. `continuity::Registry.members` carries node, lineage, hardware, generation and eligibility. `retired_continuity_v2.entries()` retains exact signed historical bindings. `endorsement_dependencies_v1::Book` retains authenticated witness/profile/historical time under `(node,lineage,generation,profilecommit)`.

Proposed pure predicate: verify class-complete authenticated physical relation against the exact parent, then resolve each canonical alias over all active, pending, retired and terminally revoked dependencies. All aliases must resolve to zero existing lineage for an independent admission, or to exactly the existing authorized lineage for an allowed rotation/recovery. Mixed existing lineages, omitted classes, an independently claimed second lineage, terminal revocation, stale authority and unauthenticated relationship refuse. Existing retired aliases remain occupied; cancellation does not erase authenticated history. The actual permitted revival/recovery rules remain those in the A2 and recovery implementations.

The check and insertion must execute in the existing clone/full-validation block boundary, inside the same canonical SQLite IMMEDIATE transaction that publishes canonical block, state, undo and operation index. Do not pre-reserve canonical lineage using the local challenge map. Parallel client attempts can generate distinct local challenges, but only one independent pending/active lineage can commit. Failed transitions and crash/reopen must retain all existing money/history and recorded revocations. A derived lookup index may accelerate this predicate but never authorize from a peer or cache.

No new StateRoot record/carrier/fee is selected here. Existing profile identities, signed current/retired bindings and A2 authenticated dependency records are the integration substrate. If the approved physical relation needs additional consensus-authenticated evidence unavailable in those carriers, identify that exact missing field and policy decision before choosing a replacement carrier.

### Exact missing verifier authentication/availability contract

For Genesis, the existing ceremony policy can designate the local verifier under its already authorized scope, with independently checked identities and actual returned-secret verification. This does not authorize extending that verifier's unilateral admission power after sealing. The local workflow can be used in the ceremony without pretending its observation is a transferable TPM proof.

For post-sealing admission, the unresolved contract is concrete: which already authenticated canonical role may issue a challenge and attest to its recovery; which exact parent-bound transition/ordered classes/AK/profile/enrollment/session the verifier signs; how a validator verifies that role was eligible at the governing parent and not revoked; where the public encrypted-object bindings and verdict remain durably available for replay/recovery; and what the network assumes about verifier honesty and secret retention. A supplied public success signature merely authenticates that signer's assertion; it does not let later validators reproduce the private challenge check. The candidate cannot secretly choose that trust assumption.

A reviewable mechanism can use existing canonical role identities and the existing finality authorization, while each designated verifier independently performs this private challenge workflow. However, no new verifier set, quorum, timing window, result-signature domain, verdict carrier or evidence-withholding rule is adopted in this tranche. Before wiring, supply the exact approved verifier-role rule, signing domain/payload and evidence availability route (an existing carrier if it can carry all necessary authenticated bindings). The replay verifier would then validate the complete signed scope and eligibility under that explicit trust model; it must still describe the private activation fact as relying on that model. The current `ActivationRecord` has no session, parent/transition, verifier identity or verdict authorization fields and cannot implement that contract unchanged just by appending a witness signature out of band.

## Prepared software and later physical controls

Source-only software controls cover exact context/transition substitution, one-shot response consumption/replay, malformed and incomplete class responses, wrong raw secret, changed current parent, duplicate EK identities, partial adapter failure, capacity refusal, restart forgetting pending attempts, and successful forwarded *modeled* delivery independent of node location. Additional integration controls require real current signed binding/owner and both hybrid signature halves, actual A2 canonical race/cancellation/revocation/history/money and crash/reopen transactions. No prepared assertion is reported as passed.

Actual physical controls must establish imported/public-only/unrelated software AK refusal, same-AK multi-class relationship qualification, unauthorized EK/AK substitutions, real forwarded activation and at most one pending/active canonical lineage. The software adapter is clearly TEST-VALUE and cannot emit a physical qualification capability.

## Primary references consulted

The official [makecredential documentation](https://tpm2-tools.readthedocs.io/en/stable/man/tpm2_makecredential.1/) documents generation using the EK public key and credentialed object Name, including no-TPM generation. [activatecredential](https://tpm2-tools.readthedocs.io/en/stable/man/tpm2_activatecredential.1/) documents recovery and warns that cpHash-only operation does not execute the command. These explain the adapter contract, not a local installed-tool claim.

[TCG TPM Library Part 1 v185](https://trustedcomputinggroup.org/wp-content/uploads/Trusted-Platform-Module-2.0-Library-Part-1-Architecture_Version-185_pub.pdf), sections 20.6, 21 and 26, describes nonduplication attributes, credential protection and public-only external loading. Public-only attribute bytes require care; the implementation must qualify actual command/authentication behavior, not infer residency from advertised bits alone. The credential provider can know recovery succeeded but cannot turn its own chosen credential into a trust-free transferable proof.

[TCG EK Credential Profile v2.7](https://trustedcomputinggroup.org/wp-content/uploads/TCG-EK-Credential-Profile-for-TPM-Family-2.0-Level-0-Version-2.7_Pub.pdf), sections 2.1/2.2 and 5, describes multiple EKs/templates and their credentials. It supports the need for complete authenticated class relationships, not a universal one-key chip identity. The [Microsoft reference ActivateCredential implementation](https://raw.githubusercontent.com/microsoft/ms-tpm-20-ref/main/TPMCmd/tpm/src/command/Object/ActivateCredential.c) validates the decryption object and recovers against the credentialed object's Name; the [LoadExternal implementation](https://raw.githubusercontent.com/microsoft/ms-tpm-20-ref/main/TPMCmd/tpm/src/command/Object/LoadExternal.c) distinguishes public-only and sensitive external loads.
