# P-LANE-DESIGN-AMENDMENTS-V1: accepted amendments to P-LANE-DESIGN-V1.md (Cipher, 2026-10-04)

Source: the independent adversarial review of the design (`P-LANE-DESIGN-REVIEW-1.md` in this directory; reviewer: a fresh agent that did not write the design; about 280 citations checked, 2 blockers, 6 majors, 11 minors, 3 nits).
These amendments OVERRIDE `P-LANE-DESIGN-V1.md` wherever they differ. Every implementation work package (WP) reads this file after the design. Evidence class: design decisions only; nothing here is implemented.
Items that need the Architect are marked **ARCHITECT** and collected in section C; each carries the default the implementers use meanwhile (reversible, isolated).

## A. Accepted amendments

**AM-1 (BLOCKER-1, pool capacity and cost; replaces the capacity text of 5.4).**
(a) Only rows in status PENDING count against `MAX_LIFECYCLE_ROWS` (65,536) and `MAX_PENDING_BYTES` (64 MiB). (b) A row that reaches a terminal state (CONFIRMED, EXPIRED, CONFLICTING, REJECTED) is COMPACTED in the same SQLite transaction: its raw bytes are replaced by NULL (schema:
`raw BLOB CHECK((status='PENDING') = (raw IS NOT NULL))`) and its resource reservations are released; id, kind, window, status, reason and height remain, so the lifecycle record is never evicted silently (CANONICAL-RETENTION-AND-CAPACITY-V1, "Pending transaction
intents": never evict silently; terminal records remain). (c) Total size stays bounded by the existing database storage budget (`DATABASE_BYTES` 128 MiB through `configure_storage_budget`); reaching it is the spec's local capacity stop ("not a consensus integrity halt";
operators provision capacity or perform a separately qualified archival upgrade). No archival/deletion policy for terminal rows is designed here: it would conflict with that spec text and is an open **ARCHITECT** item (C.1). (d) A successful signature verification is cached in the row
(`sig_ok`, valid only for that id and wire hash); reconciliation re-runs ONLY the state-dependent checks (window, inputs, authority generation, sequences, preconditions). Every kind therefore exposes two entry points, `verify_signatures` (stateless) and `verify_state` (state only), and
`verify` = both; WP-B, WP-R and WP-T1 provide them for their kinds, WP-POOL consumes them.

**AM-2 (BLOCKER-2, relay; replaces the relay paragraph of 5.3).** NO node-to-node relay in candidate 3. The wallet submits kind-1/kind-9 objects directly to the nodes it talks to (the per-peer queue of a wallet link is not shared with consensus peers) and polls kind-10/11 status. The pinned-peer
`ObjectQueue` (8 objects / 4 MiB per link, both directions, all kinds) cannot carry relayed traffic without letting an attacker starve votes/proposals/blocks; relay needs its own budget (separate per-peer relay queue or reserved slots for kinds 3, 4, 7, 8, pull-based announcement, per-peer rate
limit) and is NOT implemented. Consequence, stated plainly in the docs and in the residual list: an item reaches a block only if the node that holds it proposes (or the wallet submits to the eventual proposer). **ARCHITECT** C.2.

**AM-3 (MAJOR-1, block assembly; amends 5.5).** The assembler keeps `MAX_PREVIEWS = 128` trial additions per candidate but divides them by class: fee-free structural kinds (dividend claims, Unbond/Withdraw, Worker assignments) get a reserved share of 32 trials and are tried first; the remaining trials go to the other
items. Within each class: descending fee per byte (a proposer-local selection rule, no new fee, no consensus effect), then id. Test: 200 pending transfers + 1 claim -> the claim is included. Amend (imported copy) HYBRID-TRANSACTION-ADMISSION-V2 L41 (id-order selection). Pool operations are inserted BEFORE the trailing participation
acknowledgements (m2: `BlockBody::encode` rejects any non-acknowledgement after an acknowledgement). Fee previews use the item's DECLARED fee; the complete trial execution validates it (the preview ran trades on the PARENT state and could reject a sale that P5 evaluates after epoch events).

**AM-4 (MAJOR-2, reference History entry points; extends 1.a.3 and WP-P0).** The public `CanonicalStore::evidence_history(height, operations)` takes operations only and `counter_voter_v2.rs:420-430` (`rotate_finalized_inner`) re-validates a finalized block through it; `execution::execute_hybrid_transfers` (public, no anchor/History) is unaddressed. WP-P0 changes
`evidence_history` to take the whole `BlockBody`, fixes the counter voter, defines the behaviour of `execute_hybrid_transfers` for kind-25 items (it receives the History or refuses non-parent references), and writes the ENTRY-POINT MATRIX test: one block whose envelope item references an older height is accepted by
`commit`, `verify_replay`, `validate_round_proposal`, `validate_work_custody`, `validate_observation_v2`, `prepare_pending` (caller items and pool items) and the counter-voter migration, and each mutant "entry point without anchors" fails a named test. `reference_must_be_canonical` goes through the real
`CanonicalStore::commit`, not a hand-built History.

**AM-5 (MAJOR-3, P8 receipts for neutralized bond commands; replaces the receipt rule of 9.2/9.6 for kinds 19/20).** A bond command is validated against the PARENT lot and then skipped when same-block evidence burned the lot (`bond_ops_v2.rs:383-391`). Receipts of kinds 19/20 therefore carry an EXECUTION OUTCOME byte (1 Applied, 2 NoEffectBurned) recorded at commit from the settlement
(`CommandSettlement` gains per-command outcomes: WP-B), written into the index in the same transaction, checked by `verify_replay`; the withdrawal payout coin exists only for Applied. A wallet confirms a node's claimed record against its OWN replica's index (derived by the replica's own execution), and `verify_in_block` is limited to structural
checks (position, wire hash, id). Test `withdraw_with_same_block_evidence_records_no_effect`. WP-IDX therefore starts after WP-B.

**AM-6 (MAJOR-4, P7 maker signing key).** DEFAULT (reversible, isolated in `Domain::role()` and one wallet capability): maker offers and fill proofs are signed by the maker's WALLET OWNER key under two NEW crypto-v2 domains `MUTINY-BUILD8-TRADE-OFFER-V1` and `MUTINY-BUILD8-TRADE-FILL-V1` (role WalletOwner; the D1 packet's own names; no
new key, no node/transport identity involved, wallet custody boundary unchanged); `maker_trade_descriptor` of OfferBody v2 becomes the maker's wallet descriptor (current authority). The D1 packet section 10 PROPOSES a separate crypto role 7 "Trade" (all entries "PROPOSED / UNALLOCATED"); this is the **ARCHITECT** question C.3. WP-T4 implements the default; the
two crypto-v2 domain additions are WP-T4's only crypto-v2 edit (registry + role mapping + domain-bytes test).

**AM-7 (MAJOR-5, embedded C).** `transport-v2/embedded/worker_frame_v2.c:33-35` enforces the same `valid_until_height` session expiry as the Rust `matches_current`; WP-Q17 changes BOTH sides and their agreement tests (`worker_frames_c_tests.rs`). `transport-v2/embedded/object_control_v2.c` hardcodes object kinds 1..8 and kind 1 at 2 MiB while TRANSPORT-OBJECTS-V2 L135/L178 require Rust and embedded C to agree:
WP-NODE adds kinds 9-11 and the 16 KiB bound for kind 1 to the C side with C/Rust agreement tests.

**AM-9 (minor findings).** m1: the index table makes 20 schema objects (table + automatic composite-key index + named index), not 19 (declare it WITHOUT ROWID only if the implementer prefers 19; the count in `store_schema_v2` follows the SQL actually declared). m3: resource tags per kind are explicit and only the signer-owned
resources are reserved: transfers/rotations/bond creates reserve their INPUTS and (rotation) the wallet authority, bond commands the lot, claims the claim slot, trading items the lock/offer single-fill/License as the design says, and a precondition (such as a TreasuryHead) NEVER reserves a resource; only TreasuryRotate (R2) reserves the Treasury head, so one pending taker cannot block others.
m4: see AM-10. m5: the retention spec gets the row "reference lookups depend on the complete canonical block-hash prefix" (WP-P0). m6: the composites define PARTIAL objects (unsigned body + per-slot optional signatures) and a read-only PREFLIGHT (`preflight(state, parent, history)`: every check except missing signatures; provided signatures are verified) for sponsor/new-key/co-signer review (W12);
WP-B and WP-R implement them; `signed_len(unsigned)` (the fee rule needs the complete signed length before signing) is provided for every composite. m7: a StatusReport carries at most 32 entries. m8: a version-3 store holding retired formats is REFUSED on migration with a clear error (it cannot pass `verify_replay` under the new rules). m9: claims keep spending Treasury coins oldest generation first (no rule change); a claim
can consume inputs of a pending Treasury spend: the pool cannot predict it, the block trial skips the loser, the pool reports CONFLICTING(InputSpent) and the wallet re-signs: documented limitation and a test (`claim_and_r1_in_one_block`). m10: P6 restore evidence is a Treasury-tool obligation with an explicit record (plan id, authority id, new descriptor hash, derived-from-backup check result, tool version): defined by Lane W (W14/W17), not consensus-checkable, stated as such.
m11: kind 24 charges 1 atom per byte of the complete signed operation, the existing rule that every transaction and the funded rotation already follow; it is not a surcharge or a new recipient (informational **ARCHITECT** C.5). n1: every nested unsigned/body byte string is separately `canonical()`-checked (the walker does not recurse into byte strings). n2/n3: documented.

**AM-10 (m4 and Q17(d), assignment delivery window): NOT relaxed.** `effective_epoch == inclusion_epoch + 1` stays (a locked V2 rule; the relaxation proposed in 11.2(d) would change locked text and needs an upper bound that the Order says to identify, not invent). WP-Q17 keeps the equality, documents the one-epoch window as a known limitation of the Worker-assignment product path, and provides the pool/wallet with the facts needed
to re-sign. Everything else of 11.2 stands ((a) sale cancels a committed pending assignment; (b) session expiry divergence on BOTH Rust and C sides; (e) boundary text). **ARCHITECT** C.4: the identified missing bound is the maximum lead of `effective_epoch` over the inclusion epoch; proposal: allow `inclusion_epoch < effective_epoch <= inclusion_epoch + L`, L chosen by the Architect (unit: MiningEpochs).

**AM-11 (test corrections).** The 14.3 trading zero-destination rows: a trading item that fails `NativeOperation::decode` makes `BlockBody::encode` fail, so no block exists; assert (i) the codec/`NativeOperation::decode` refusal, (ii) that `BlockBody::encode` refuses a body carrying it, and (iii) the defensive `credit` check at unit level with a crafted internal call. The 14.5 `prepare_batch` assertions cannot reproduce staleness caused by the sale block's
own epoch (prepare_batch uses the parent as tentative): for those cases assert the block-level rejection AND the exact `NativeError` by building the tentative state the way the executor does (epoch advance first) before calling the apply path. Add the missing negative cases listed by the review: P2 inputs from older wallet generations (payer 0 and payer 1); a Treasury R1 spending reserve; a kind-24 input CREATED at height H (`<` vs `<=` mutant); trading `Applied` and claim-sequence replay under envelopes;
same-block combinations (FundedRotation + kind 24 of one owner, R1 + R2, claim + R1); kind 24 without Continuity and in a recovery block; far-future activation epoch (kept rejected); pool lifetime/exhaustion, class starvation, acknowledgement ordering. The skeleton's pairwise-disjointness test is NOT evidence: WP-B and WP-R each write a CROSS-VERIFY MATRIX test against the REAL payload builders available on their branch (every `Domain::Transaction`
payload: transfer input, trading approval, dividend claim, Treasury freeze and the new funding payload: a signature made for one must fail every other verifier), and Cipher runs one combined matrix at integration.

**AM-12 (direct user decision during the Codex takeover, 4 October 2026).** Unfunded offers stay above consensus. First canonical funding requires the maker's current WalletBook authority at the existing trading phase, before payment transactions. Retired-only offers cannot first fund even with current settlement approvals or an old finalized reference; obtain a newly reviewed/current-signed offer. This supersedes the earlier T4 rotation-positive and Forge's proposed pre-rotation commitment requirement. No new commitment kind/carrier/fee. Already finalized locks retain exact terms, destinations, deadlines and existing claim/refund authority through rotation. See CODEX-TAKEOVER-DECISIONS-20261004.md for required before/after/same-block/pending tests.

## C. Questions for the Architect (each with the default being implemented)
1. Archival rule for terminal pool rows (conflicts with CANONICAL-RETENTION L14 if it deletes): default = compact, never delete; capacity stop at the storage budget.
2. Node-to-node relay of pool items: default = not implemented in candidate 3; relay needs a separate budget design (residual launch dependency).
3. P7 maker signing key: default = wallet owner key under new domains TRADE-OFFER-V1 / TRADE-FILL-V1; alternative = the D1 packet's separate role 7 "Trade" (crypto-v2 role/derivation/custody change).
4. Worker assignment lead bound L (epochs): default = none (exact next epoch, locked rule); the one-epoch delivery window is a known limitation of the usable marketplace.
5. Fee statement: kind 24 pays 1 atom/byte of the complete signed bytes (existing rule, no surcharge).
6. (from the design) R2 needs only the current canonical Treasury key's approval and routes only to its current generation; restore evidence is a Treasury-tool record (W17); Restart Order L64: a sale cancels a committed pending old-owner assignment; transfers and dividend claims keep their signed windows without reference/preconditions; legacy V1 transfer unchanged (retired path).
