## 1. What this package changes, and what it does not

Consensus validity no longer depends on any build flag.

* The three consensus features `trading-candidate`, `trading-qualification` and `trading-license-hook` are deleted from `consensus/Cargo.toml`. The code they gated (`trading_v1`, `trading_host_v1` operation/records/execute, `state_records`, `license_book_v2` including the `Book::validate` clause for detached Licenses and `transfer_candidate`) is always compiled.
* Rationale: the locked decision documents (`spec/ARCHITECT-DECISION-LOCK-RESTART-ORDER-V1.md`, `spec/ARCHITECT-TRADING-DECISION-LOCK-20261001.md`) make DvP/conditional-MUT trading, License and dividend operations part of the day-one protocol, so trading validation belongs to the always-on rule set (option (a) of the analysis). Before this change a default-feature validator, a `trading-qualification` validator and a `trading-license-hook` validator disagreed on the first block with a trade, on State restore, and on the StateRoot of a transferred License.
* The node feature set is now one SERVICE-ONLY feature, `trading-service`. It forwards nothing to consensus and gates exactly two items: the module `trading_service_v1` and `HybridRuntime::preview_trading`. An optional wallet interface or trading service therefore cannot remove validation of otherwise valid trading, License or dividend operations.
* The qualification-only constructors (`CandidatePolicy::synthetic_one_atom_per_strike`, `OfflineSafety::qualification`, `StorageKey::qualification`, crash hooks) are `cfg(test)` only.

Not changed (stated plainly): the trading PARAMETERS. The denomination and fee constants, `native_denomination_locked()`, `MAINNET_ACTIVATION = false` and the candidate wording stay exactly as they were and remain candidate pending the pre-Genesis lock packet. Only the dependence of validity on a build flag was removed. No value or semantics changed. Protocol questions P2 (fee/denomination values) and P3 (production License suspension authorization) are not decided here. P4 (which wallet operations the wallet builds) is answered by the Architect's decision that the wallet and trading capabilities are included in the shipping configurations; this record lists them as required capabilities and does not claim they are implemented.

The `LicenseHookRequired` result (a License DvP failing closed when the hook was off) no longer exists; `NativeError::LicenseHookRequired` was removed because no code can produce it. The former default-build test that asserted it now asserts the single-build behaviour (see 5).

Historical evidence records under `qualification/nonce-20261002/` still mention the removed feature names. They record past runs and are deliberately left unedited.

## 3. Release profile (identical in the consensus, node, crypto-v2, transport-v2, desktop, release-signer and wallet-core root manifests)

| Key | Value | Reason |
|---|---|---|
| opt-level | 3 | Cargo release default, made explicit. |
| overflow-checks | true | Cargo's release default is false while every test runs with true. Consensus arithmetic must behave identically in tests and in the shipped binary. |
| debug-assertions | false | Release default, explicit. Test-only hooks are `cfg(test)`, not `debug_assertions`. |
| codegen-units | 1 | Deterministic code generation. |
| strip | "none" | The exclusion checks inspect symbols and strings. |
| lto | false | Not needed for correctness; the C sources compiled by `build.rs` make cross-language LTO an unverified variable. Revisit only together with a reproducibility test. |
| panic | "unwind" | See below. Unwind is kept in every shipped root. |

Why `panic = "unwind"` is kept (each reason was checked in source):

* Node: `node/src/peer_supervisor.rs`, `actor_service.rs` and `hybrid_peer_worker_v2.rs` detect a panicked worker through `JoinHandle::join().is_err()` and fail closed ("Peer worker panicked", "Actor thread panicked"). `panic = "abort"` would remove that supervision.
* Wallet and release signer (and the node): `crypto-v2/src/lib.rs` `private_job` runs every private-key operation (key derivation, signing, vault seal and open) on a worker thread and maps a worker panic to `Error::Worker` through `JoinHandle::join()`. With abort the same panic would abort the whole process instead of failing closed, and `Zeroizing` secret buffers are dropped (zeroized) only while unwinding.
* Wallet: `desktop/src/wallet_host_service_v2.rs` detects a panicked wallet service thread with `join().is_err()`, and the node library it links supervises its peer workers the same way.
* Abort is not provably safe, so it is not used. The table is kept identical in every shipped root so that one rule is checked everywhere (the script requires exactly these seven keys).

Dev profile: `[profile.dev.package."*"] opt-level = 3` (consensus, desktop, release-signer and wallet-core). FN-DSA, KDF and the C crypto code are far too slow at opt-level 0 in debug tests; only dependencies are optimised, so the crate under test keeps debug assertions and overflow checks. It affects test/dev builds only.

Profile tables are honoured only in the root manifest being built, so each shipped root carries the same table. `desktop/Cargo.toml` and `release-signer/Cargo.toml` received theirs (profile tables only, no dependency line, no lockfile change) after the import; that edit is recorded in `build/imports/EDITED-AFTER-IMPORT-V1.tsv` (section 10), whose desktop line also covers phase 0C's later dependency edit of the same file. `wallet-core/Cargo.toml` carries both tables (phase 1); the script requires them because `wallet-core/` exists.

### 4.1 wallet-core (UI-free library; Linux and Windows)

`wallet-core/` (package `mutiny-wallet-core-v8`) exists since phase 1 (merged at a0ecb7b; placeholder handlers for the later operation kinds at c57b45e). It carries the plan, review, authorize and sign layer for the wallet operations (today ordinary MUT payments end to end; every other kind is a registered placeholder refused as `NOT_IMPLEMENTED`) and is testable on Linux and Windows with TEST-VALUE keys. Its dependencies: consensus (default features), crypto-v2 (`wallet-custody`), minicbor, sha2, hex, zeroize and rusqlite (bundled; the durable outbox); dev-dependencies: itself with `test-value-signing` (tests only, see below), serde_json, p256. Configuration (checked, and passing on the real crate): `default = []`; the only other feature is the NON-SHIPPING `test-value-signing = []`; crypto-v2 `wallet-custody` only; consensus, node and transport-v2, if present, at default features (never `trading-service`); no GUI crate (eframe, egui, winit, glutin, glow, arboard), no `windows-sys`, no `ed25519-dalek-bip32`, no direct `bip39` dependency, no network crate (tokio, reqwest, hyper, h2, mio, socket2, ureq, curl, rustls, openssl, tungstenite, quinn, libp2p and the like), and no Bitcoin-ecosystem crate (next subsection) in ANY dependencies table of the manifest or in the resolved graph for either target. Signing works only on x86_64 (`crypto-v2` `platform.c` requires the qualified x86_64 rounding environment), so an aarch64 runner would fail every signing test.

`test-value-signing` is a non-shipping test-support feature and must never be reachable from a shipping configuration. The script enforces: `default = []` exactly and `test-value-signing = []` exactly with no other feature forwarding it; the resolved graph of wallet-core shows only `default`; wallet-core is absent from both validator graphs; a desktop dependency on wallet-core must not enable it (manifest and graph); no source `cfg(feature = ...)` other than `test-value-signing`; and, in linked executables, the marker strings `TestValueGate` and `MUTINY-BUILD8-TEST-VALUE-SIGNING` are forbidden. The contract for the code behind the feature: every item gated by `test-value-signing` must carry one of those markers (for example the gate type named `TestValueGate`), so that an executable which contains the gated code is caught. A library artefact (rlib) is NOT scanned: rustc records cfg-stripped item names and the feature name in an rlib's crate metadata, so a default-feature release rlib of a crate whose item `TestValueGate` is gated still contains both strings (observed on a stub wallet-core; scanning it would only produce false failures). Executables do not link that metadata. The non-shipping rehearsal configuration (`cargo test --features test-value-signing`) is listed under `ci-test-only` and is never built by the exclusion script as a shipping graph. The crate's own tests turn the feature on through a dev-dependency on the crate itself; resolver 2 does not unify dev-dependency features into a normal or release build, and the graph check (`cargo tree -e normal,build`) sees `default` only.

**Open finding at revision 3: the real crate does not meet the marker contract.** It gates eleven sites with `cfg(any(test, feature = "test-value-signing"))` (`src/authorize.rs` and `src/outbox.rs`); neither `TestValueGate` nor `MUTINY-BUILD8-TEST-VALUE-SIGNING` occurs anywhere in wallet-core. It defines its own marker `MUTINY-WALLET-CORE-TEST-VALUE-GATE-V1` (`src/authorize.rs`, `TEST_VALUE_GATE_MARKER`), which only `SigningGate::test_value()` references (and through it `KeySigner::for_test`); `ReviewGate::with_limits`, `present_at`, `approve_at`, `authorize_at`, `Approval::for_review_for_test` and `MemoryOutbox::corrupt_for_test` carry no marker. The crate's sources state that the production exclusion check forbids its marker in release artefacts, so revision 3 adds `MUTINY-WALLET-CORE-TEST-VALUE-GATE-V1` to the forbidden wallet-executable strings (an addition; `TestValueGate` and `MUTINY-BUILD8-TEST-VALUE-SIGNING` stay forbidden). Whether wallet-core marks every gated item or the contract is amended is a change request to the wallet-core owners and a decision for the Architect. The feature itself stays excluded at the manifest, graph and cfg level, which the script checks and which pass. Since phase 7 the desktop executable links wallet-core; with the production gates closed its release build contains no wallet-core code at all (revision 4 observation, 4.2), so none of these markers can appear in it today.

**Resolution at revision 5 (integration lead's proposal; the Architect confirms):** the contract is AMENDED, not the crate. The canonical wallet-core marker is `MUTINY-WALLET-CORE-TEST-VALUE-GATE-V1` (forbidden in every wallet executable and its pdb since revision 3); `TestValueGate` and `MUTINY-BUILD8-TEST-VALUE-SIGNING` stay forbidden as additional tripwires. Marking every gated item would add nothing the other controls do not already give: the feature cannot reach a shipping build without being named in a manifest, in the resolved graph, in a lock record or in a source cfg (all checked, with negative controls), and every gated item exists only under `cfg(any(test, feature = "test-value-signing"))` (checked by wallet-core's `build_independence` test). The binary marker is the last line of defence, not the only one.

### 4.4 The Bitcoin boundary and its single exemption

No Bitcoin-ecosystem crate (names starting `bitcoin`, `secp256k1`, `bdk`, plus `miniscript`, `psbt`, `bitcoincore-rpc`, `rust-bitcoin`, `electrum*`, `esplora*`) may be in the graph of wallet-core, the desktop or the release signer. BTC custody is external: the wallet signs MUT authority only. The literal rule "no crate named `bitcoin*`" cannot hold for anything that links crypto-v2, so there is exactly ONE exemption, found by reading the lockfiles: `crypto-v2` depends on `bip39 =3.0.0` (the 24-word wallet phrase), and `bip39` depends on `bitcoin_hashes` 0.14.101 ("hash functions used by the rust-bitcoin ecosystem": no keys, scripts or transactions) and `hex-conservative`. All six lockfiles contain them, the node validator's included. The script accepts `bitcoin_hashes` only when it is reached through `bip39` and nothing else, and `bip39` only through `mutiny-crypto-v2` (the desktop's direct V1 `bip39` dependency, tolerated only while it was recorded as pending, was removed by phase 0C). A direct dependency of wallet-core or of the signer on `bip39`, on `bitcoin_hashes` or on any other Bitcoin-named crate fails.

### 4.5 Required wallet and trading capabilities

### 6.1 Linux source-path portability (`build/check-source-paths.pl`)

Status: IMPLEMENTED (a static check, run on the Windows host; branch `integ/linux-portability`). It applies Linux path rules; it is not a Linux build and not Linux execution evidence.

Why. Every Build 8 build and test so far ran on Windows, whose path handling hides failures that stop a Linux build. rustc joins a `#[path]` written inside an inline `mod name { .. }` block to a directory named after the inline module(s), preceded by the file stem when the file is a non-mod-rs module: in `consensus/src/join.rs`, `mod tests { #[path = "../../../tests/support/software_tpm.rs"] mod software_tpm; }` resolves from `consensus/src/join/tests/`. Windows collapses `..` lexically and finds the file; Linux walks every component, `consensus/src/join/` does not exist, and the build fails with ENOENT. Windows also matches names case-insensitively. No Windows run can show either, and neither can a `cargo check --target x86_64-unknown-linux-musl` on Windows, which still uses the Windows file system.

What it checks (one perl script using only built-ins and `Cwd`; a few seconds; deterministic; `--selftest` builds scratch trees and verifies every finding class and a clean pass). Every Rust file reachable from a target of consensus, node, crypto-v2, transport-v2, wallet-core and release-signer (findings fail) and of desktop (findings are reported as windows-only and do not fail), and from the library and build script of every path dependency and `[patch]` they name: (1) `#[path]` and `cfg_attr(.., path = ..)` on `mod` items, from rustc's base directory (`rustc_expand/src/module.rs`; each rule was confirmed with rustc 1.98.1 on synthetic crates); (2) `include!`, `include_str!` and `include_bytes!` from the directory of the file that holds the call, and `concat!(env!("CARGO_MANIFEST_DIR"), "/..")` from the crate root (three such includes exist, all in node, and resolve); (3) `mod name;` (exactly one of `name.rs`, `name/mod.rs`); (4) Cargo.toml paths: dependencies of every kind, `[patch]`, `[replace]`, explicit and inferred targets, `package.build`, the workspace root that inherited keys come from; (5) a backslash or an absolute path in any of these literals; (6) shell and perl scripts: no carriage return and `#!` at the first byte; (7) names that differ only by case, a trailing dot or space, Windows-reserved names and characters; (8) build scripts: relative path literals, and every JSON source lock a build script reads must list files that all exist, with exact case, under one directory (the seven locks read by `crypto-v2/build.rs` and `transport-v2/build.rs`, 551 entries, do); (9) C and C++ `#include`s that match a tracked file only ignoring case. Resolution is component by component with exact names from the directory listing; `..` only steps out of a directory that exists; nothing may leave the repository root. In a git work tree the git index is the tree (what a clone and `git archive` contain: an untracked file or a stray local directory cannot satisfy a reference); in an extracted package the extracted files are.

Where it runs: `build/check-shipping-config.sh` (section "Source paths", git mode and package mode); the FIRST step `g0-source-paths` of `package/linux-native-test/run-linux-native-tests.sh` (recorded like every step, a finding fails the campaign, but it does not gate the compile steps g1-g9, which remain the authoritative gate; `perl` is a precondition); step `g0-source-paths` of `package/windows-wallet-test/run-windows-wallet-tests.sh`, before the provenance step; and `package/linux-native-test/build-package.sh`, which runs it on the extracted package before vendoring, aborts the build on a finding and records the checker, its sha256 and the result in `PACKAGE-IDENTITY.json` (`source_path_checker`, `source_path_checker_sha256`, `source_paths_at_build`).

Fixed with it (the only findings at 67e2463): the software TPM simulator was declared five times with a `#[path]` inside an inline test module: `node/src/main.rs` (`runtime_ingress_tests`, present since the base) and `consensus/src/join.rs`, `rotation.rs`, `recovery_material.rs` and `bond_ops.rs` (`tests`). Each crate root now declares it ONCE at file scope under `#[cfg(test)]`: `consensus/src/lib.rs` `#[path = "../tests/support/software_tpm.rs"] pub(crate) mod software_tpm;` (the four test modules `use crate::software_tpm;`) and `node/src/main.rs` `#[path = "../../consensus/tests/support/software_tpm.rs"] mod software_tpm;` (re-exported as `pub(super) use super::software_tpm;` in `runtime_ingress_tests`, so the path `runtime_ingress_tests::software_tpm` used by `custody_configuration_tests` is unchanged). No test, test name or shipping item changed. Windows outcomes before (67e2463) and after are identical test by test: consensus `--lib` 189 tests (186 passed, 3 ignored), node `--bin mutinyd-v8` 11 passed; the warnings of both builds are unchanged.

Negative controls (`build/negative-controls.sh`, `paths_*`): the unmodified scratch clone passes and `--selftest` passes (positive controls); the check fails, with the expected `path:line` message, for an inline-module `#[path]` with `..` (in `consensus/src/join.rs`), a wrong-case `include_str!` path, a wrong-case `#[path]`, a wrong-case Cargo path dependency, a CRLF shell script, two tracked names that differ only by case, an `include_str!` of an untracked file, the inline `#[path]` in an extracted package (file-system mode, which passes unmodified), and through `build/check-shipping-config.sh`.

Limits (stated in the script header): macros are not expanded (`mod` items and `#[path]` produced by `macro_rules!`, and include arguments built from macro variables, are not resolved; the latter is reported with `--verbose`); cfg handling is coarse (only a cfg that is false on x86_64 Linux makes a finding windows-only); paths computed at run time (`Path::new(env!("CARGO_MANIFEST_DIR")).join(..)`, file reads, arguments) and build-script logic beyond literals are not resolved; symbolic links are not modelled (the tree has none). It cannot see linker, system-library, kernel, permission, timing, locale or environment differences: only a Linux build and test run shows those.

## 7. Recommended follow-up: compile-time rule-set identity (not implemented)

The PROPERTY is the type system. A wallet key reaches a signature only through `Signer::authorize`: the handlers get the key as wallet-core's crate-private `KindSigner`, whose domain `domain_for` derives from the operation kind and the purpose (no caller supplies one), and only with a single-use `Approval` that is not `Clone`, has private fields and is issued only by the review gate (`ReviewGate::approve`, through `PlanSession::approve`). The tripwire, `build/check-signing-calls.pl` (perl built-ins and `Cwd` only; a few seconds; deterministic), catches a NEW call site that could sign outside that path whatever its receiver is called. A line break is a space, so a split method chain is read like any other. The signing names are listed in `build/signing-call-rules.txt` (`callee sign`, `callee approve`, `prefix sign_`): they cover `HybridKey::sign`, `Transfer::sign_input`, `trading_v1::Operation::approve`, `Rotation::sign`, `SignedClaim::sign`, `OfferProof::sign`, `SignedOffer::sign`, the bond operations' `sign` and `treasury_proof_v1::sign_challenge`, and the other consensus signing routines (`sign_probe`, `sign_work_probe`, `sign_authorization`, `sign_possession`). A signing call is a method call `.name(` (also `.name::<..>(`), any path segment `::name` (called or not: `HybridKey::sign` as a function value, `<T as U>::name`, a `use` of it) or a bare `name(` that is not its definition; each is attributed to the innermost enclosing `fn` (brace-tracked, closures belong to their `fn`).
