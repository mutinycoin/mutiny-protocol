DECISION 2 — GENESIS-RELATIVE MINING EPOCHS
======================================================================

APPROVED.

Consensus block timestamps are:

unsigned 64-bit Unix seconds.

Genesis commits the authoritative:

t0 = GenesisTimestampUnixSeconds.

For every post-Genesis candidate:

candidate_timestamp >= t0

and:

MiningEpoch =
floor((candidate_timestamp - t0) / 60).

All arithmetic is checked integer arithmetic.

A candidate timestamp before t0 is invalid.

======================================================================
2B. WHO CHOOSES CANDIDATE TIMESTAMP
======================================================================

The ESP32 Miner MUST NOT freely choose candidate_timestamp.

The coordinator/node constructs the candidate work authority and chooses the

The Miner varies only the authorized PoW search field(s), principally nonce.

Therefore a Miner cannot:

alter timestamp to obtain different work validity.

======================================================================
2E. MEDIAN-PAST RULE
======================================================================

Preserve the approved median-past-11 timestamp rule.

Codex must encode the exact early-chain rule as:

For candidate height h:

collect timestamps from up to the previous 11 canonical blocks.

For heights where fewer than11 prior canonical blocks exist:

use ALL available prior canonical timestamps, including Genesis height0.

Compute the deterministic median according to the canonical integer ordering.

Candidate timestamp must satisfy the exact technical-annex relation to that
median.

If the annex currently says "strictly greater than MTP", preserve that exact
relation.

Do not silently change >= versus >.

AMENDMENT D3 (2026-10-03), in addition and without weakening the rule above:

A child block's timestamp must be at least its parent's timestamp (equal is
permitted). The median-time-past rule above ALSO applies, unchanged (strictly
greater than the median), so a timestamp equal to the parent's is valid only
when it is also strictly greater than the median.

Implementation note (equivalence, not a second rule): implementations may test
"timestamp >= maximum of the ancestor window" provided the window includes the
actual parent and contains only validated ancestors of that parent. On a chain
built under this rule the parent's timestamp is the window maximum regardless of
window order. This equivalence is NOT claimed for any chain containing a block
whose timestamp precedes its parent's; such a chain is not valid under this rule.
Both canonical stores enforce the condition (see
D3-TIMESTAMP-ADMISSION-AMENDMENT-AND-EVIDENCE-20261003.md).

2F. TWO-HOUR FUTURE HOLD  --  SUPERSEDED BY AMENDMENT D3 (2026-10-03)
======================================================================

AMENDED TEXT (authoritative):

There is NO wall-clock future hold. The local 7,200-second admission/relay
hold on unfinalized candidates and proposals is removed. A validator's
willingness to SIGN a fresh block vote is governed solely by its qualified
clock (block.timestamp <= qualified_local_UTC_now, zero allowance), never by
admission. Stale unfinalized proposals are excluded by height, round, parent and
lock checks, not by wall-clock age. Authenticated finalized ingestion and
historical validation never read a receiver clock. The two concepts remain
separate: (a) consensus timestamp validity is the deterministic rules of
section 2E, evaluated identically by every validator; (b) local voting
eligibility is the qualified-clock guard.

SUPERSEDED TEXT (historical, preserved verbatim; no longer in force):

    Preserve the already-approved local two-hour future-hold behavior exactly as
    specified by the technical annex.

    It is NOT permitted to become an undocumented new consensus validity rule.

    Document clearly whether it is:

    local admission/relay hold policy

    versus

    historical consensus invalidity.

    Do not mix those concepts.

DECISION 3 — EXACT 60-BLOCK RETARGET
======================================================================

APPROVED.

InitialPoWTarget applies to:

heights1..60.

A difficulty adjustment occurs after each canonical height h where:

h mod 60 == 0.

The resulting target applies beginning at:

h + 1.

Therefore retarget boundaries are:

after60 → target for61..120

after120 → target for121..180

after180 → target for181..240

and so on.

======================================================================
3A. TIMESTAMP ENDPOINTS
======================================================================

For retarget boundary height h:

start_timestamp =
timestamp[h - 60]

end_timestamp =
timestamp[h].

Thus the first retarget uses:

timestamp[0] = Genesis t0

and:

timestamp[60].

This measures exactly:

60 canonical block intervals.

Do NOT use:

timestamp[h-59]

because that represents only59 adjacent block intervals.

======================================================================
3B. EXPECTED SPAN
======================================================================

Target block interval:

60 seconds.

Blocks per retarget interval:

60.

Expected span:

3600 seconds.

======================================================================
3C. ACTUAL SPAN
======================================================================

Compute using a signed/wide checked intermediate:

raw_span =
signed_wide(timestamp[h])
-
signed_wide(timestamp[h-60]).

Then:

s = clamp(raw_span, 900, 14400).

Therefore:

minimum effective span:
900 seconds = 1/4 expected

maximum effective span:
14400 seconds = 4x expected.

If raw_span is zero or negative due to otherwise-permitted timestamp geometry:

the deterministic clamp produces:

s = 900.

Do not underflow unsigned arithmetic.

======================================================================
3D. TARGET CALCULATION
======================================================================

Let:

old_target

be the authoritative target applying to block h.

Compute:

raw_next =
floor(old_target * s / 3600).

Use a sufficiently wide integer intermediate so:

old_target * s

cannot overflow.

Then:

next_target =
clamp(
    raw_next,
    1,
    2^256 - 1
).

The resulting uncompressed 256-bit target is consensus-authoritative.

No floating point in consensus.

No displayed "difficulty" value is authoritative.

Select one exact relation and encode edge vectors for:

======================================================================
3F. QUORUM PAUSES
======================================================================

APPROVE:

retarget timestamp span INCLUDES time during Continuity quorum pauses.

Do NOT subtract:

local WAITING_QUORUM duration
observer-local outage time
node-local disconnected time
radio outage measurements.

There is no separate consensus-certified pause accumulator.

Therefore the authoritative retarget span is simply:

subject to the approved clamp.

A sufficiently long quorum halt may therefore ease the next retarget by up to
the existing4x interval clamp.

This is intentional for Build8 V1.
