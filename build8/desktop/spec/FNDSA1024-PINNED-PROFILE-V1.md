### Fixed-width Bernoulli comparison hardening

The current gated Rust signing candidate uses a fixed-width comparison in the
integer-backend Bernoulli path. For the unchanged finite threshold `z`, it consumes
exactly eight successive PRNG bytes, interprets them as an unsigned big-endian
64-bit integer `u`, and accepts exactly when `u < z`. Equality rejects. Thus its
acceptance probability under ideal uniform bytes remains exactly `z / 2^64`.
Threshold arithmetic, the 79-bit base table, key generation, recovery derivation,
key/signature encodings and verification rules are unchanged.

This replaces the early-exit byte comparator after an exact joint trace review
found that equal comparison-length and acceptance marginals do not establish
joint independence. Fixed byte consumption changes subsequent PRNG positions and
deterministic signing transcripts. It does not change the verifier suite identity
or require different wallet recovery keys. The exact local source revision is
committed by `FNDSA-CUSTODY-SOURCE-LOCK-V2.json`; that lock and this profile enter
the pre-Genesis ProtocolFingerprint candidate inventory.

The replacement public sampler and signature vectors were generated by a
separately patched scalar C path using the unchanged published upstream inputs.
The C/Rust paths and Windows/Linux hosts agree, including 128 synthetic
1024-degree signatures. The nine Rust signing-library tests pass. The original
two transcript failures are retained in qualification evidence rather than
hidden. The public 512-degree vector is a library test only, not a permitted
Build8 production key size.

Source promotion is not production security qualification. Accepted-key numerical
ranges, the full rejection/signature distribution and complete target timing
remain open. Neither the fixed comparison nor functional interoperability proves
those properties. `PRODUCTION_SECURITY_QUALIFIED` remains false.

## Parameters and encodings

Only logn=10, n=1024, q=12289 is accepted. Degree 512 and toy degrees are rejected
at the Build8 boundary even if a library's generic Standard API accepts them.

Public key: exactly 1793 bytes, header 0x0a, followed by 1024 canonical 14-bit
little-endian coefficients in the pinned bit-reversal NTT representation. Each
coefficient must be less than 12289. No alternate polynomial-domain encoding.

Private key: exactly 2369 bytes, header 0x5a; signed f and g coefficients packed
at five bits each, F coefficients at eight bits, followed by the 64-byte
SHAKE256 hash of the exact encoded public key. G and the public key are derived
and checked by the pinned implementation. The pinned decoder does not check the
stored public-key hash; the Build8 adapter must recompute that hash and compare
the derived public key with the expected public descriptor before signing.
Secret encoding is custody-internal,
never a network object or evidence artifact.

Signature: exactly 1280 bytes, header 0x3a, 40-byte nonce, canonical compressed
s2 and zero padding to the exact length. The compression uses least-significant
bits first: sign bit, seven low magnitude bits, then unary high magnitude.
Negative zero, out-of-range magnitude, insufficient data and nonzero trailing
padding are invalid. The infinity norm bound is 840; squared combined norm must
be at most 70265242, with overflow-safe validation.

## Hashing and signed-message mode

Build8 uses the library's RAW mode with EMPTY context, exclusively. The message
is a 64-byte SHA-512 protocol intent. Its role-specific canonical preimage binds
the suite and all required network/Genesis/protocol/generation/object fields.
Both Ed448 and FN-DSA authorize that same protocol intent. The external-mu and
library prehash/OID APIs are not exposed to untrusted callers. Their existence in
the underlying library does not make them valid alternate Build8 modes.

For exact encoded public key PK and 64-byte intent M:

Hpk = SHAKE256(PK, 64 bytes)

mu = SHAKE256(Hpk || 0x00 || 0x00 || M, 64 bytes).

The first zero denotes RAW, the second the zero-length context. Hash-to-point
uses SHAKE256(nonce40 || mu64). Parse successive little-endian 16-bit values,
reject values >=61445, and reduce accepted values modulo 12289 until 1024
coefficients exist. These semantics come from pinned util.c/comm sources;
application code must not replace their mathematical implementation.

## Key generation, signing and recovery

Key generation consumes one 32-byte seed and deterministically derives the exact
encoded keypair using the pinned integer key-generation algorithm. Production
fresh keys obtain independent OS-CSPRNG-backed seeds. Wallet recovery uses its
separately locked BIP39/HKDF-SHA512 derivation; a recovery seed is not a generic
production RNG fallback and cannot be shared across roles or algorithms.

Signing obtains 40 fresh random bytes and uses the pinned hedging construction
SHAKE256(SHAKE256(encoded f || encoded g,40) || mu || randomness40,40), followed
by the pinned retry/sampler algorithm. Production entropy failure must abort
before signing, never fall back to a constant/test RNG. Valid signatures need
not be byte-identical across invocations. Verify every newly created signature
before export to contain detectable signing faults. Caller-owned private buffers
must be zeroized; remaining library-local copies require the security review.

Keygen and verification use integer arithmetic. The pinned algorithm implements
binary64 round-to-nearest/ties-to-even signing arithmetic. The current Build8
candidate selects its existing integer emulation on every supported signing
target through the hash-locked `integer_backend` selection, as recorded in
FNDSA-INTEGER-BACKEND-CANDIDATE-V2.md. Native floating-point signing observations
are historical evidence, not the selected production candidate. No fast-math,
reassociation, fused operations or unreviewed rounding mode is permitted.
Compiler/CPU configurations require qualification; functional vectors alone do
not establish side-channel safety.

## Verification and qualification boundary

Require exact key/signature lengths and headers before library decoding. Reject
unknown profile/suite, malformed key, wrong role/context/intent and invalid norm
or signature. No Ed25519, lower-degree or single-half fallback. A hybrid verifier
must check Ed448 as well; FN-DSA alone grants no authority.

Existing C/Rust positive and mutation vectors, non-AVX2 tests and independent
Python message-representative checks are qualification evidence, not production
approval. The actual ESP32 RAM verifier probe measured approximately 23.52 ms
per FN-DSA verification at 80 MHz, with a 4127-byte caller workspace. This does
not establish final watchdog, full task stack, calibrated power or Ed448/hybrid
update integration. The source security review and profile wrapper remain gates.

## Gated initial LDL domain guard

The gated source revision recorded in
`qualification/sampler-initial-ldl-promotion-v2.json` checks the degree-1024
key-only initial Gram decomposition before target calculation or sampling.
Unsupported initial product domains cause signing failure before private output
is exported. The guard neither clamps arithmetic nor substitutes samples or
retries with new signing randomness. Key derivation, recovery, encodings and
verifier acceptance are unchanged. Supported public signing transcripts match
the previous fixed-eight-byte comparator corpus.

The selected emulator's signed-zero conventions require precise qualification:
division with a zero numerator returns positive zero, and square root of
negative zero returns positive zero. These differ from strict IEEE signed-zero
outputs. The retained exact-oracle review is
`qualification/flr-zero-sign-review-v1.json`. Identified scalar signing divisions
use numerator one; sampler square roots require positive LDL pivots. Those
domain restrictions, rather than a blanket IEEE-conformance claim, govern the
remaining source review. The floor operation also maps negative zero to minus
one, so its resulting fractional center is one. Rounded fractional-center bounds
must include that endpoint.
